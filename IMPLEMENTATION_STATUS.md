### Two real bugs caught and fixed during this phase (not just written — actually caught by running tests)

1. **UUID binding across dialects.** The first version of every FK/PK column used `PG_UUID(as_uuid=True).with_variant(Text(), "sqlite")`. Under SQLite this tries to bind a raw Python `uuid.UUID` object into a driver that only accepts int/float/str/bytes/None — it would have failed the moment a table with a Postgres-vs-SQLite-variant column was ever written to outside Postgres. Fixed with a proper `GUID` `TypeDecorator` (`app/models/base.py`) that explicitly converts `uuid.UUID <-> str` for non-Postgres dialects.
2. **Async lazy-loading (`MissingGreenlet`).** Two tests failed when accessing an unloaded SQLAlchemy relationship attribute (e.g. a backref collection) directly under `AsyncSession` — this is a real, easy-to-hit bug class in any async FastAPI + SQLAlchemy app, not specific to this test suite. Fixed by (a) adding `AsyncAttrs` to `Base` so future code has a supported async-safe lazy-load path (`await obj.awaitable_attrs.x`), and (b) correcting the tests to use explicit `selectinload()` eager-loading, which is the pattern the repository layer already follows correctly.

### Verification scope — what SQLite testing does and doesn't prove

**Proven by the SQLite test suite:** table structure, column types, relationships (one-to-many, many-to-one, one-to-one), cascade deletes, unique constraints, the repository query patterns, and the pgvector-fallback round-trip at the Python/ORM level.

**NOT provable without a live Postgres+pgvector instance** (need to be verified by you, same as Phase 1's Docker verification):
- `alembic upgrade head` actually succeeding online (vs. the offline `--sql` render already verified)
- The `ivfflat` vector index actually being created and usable
- Postgres-native `ENUM` type creation/enforcement (SQLite falls back to plain `VARCHAR`, which doesn't enforce the allowed value set)
- `scripts/seed.py` actually inserting rows successfully
- Real query performance / index usage

### Bug found and fixed during your first attempt at this step

Your first run surfaced two real issues, now fixed:

1. **`make migrate`/`make seed` assumed a local Python environment on your
   host machine** (`alembic: not found`, `python: not found` — Ubuntu ships
   `python3`, not `python`, and you'd never installed the backend's Python
   deps locally since you'd only ever used Docker). Fixed: these targets
   now run `docker compose exec backend ...` — inside the already-built
   backend container, which has everything installed.
2. **The backend Dockerfile never copied `alembic.ini` into the image** —
   a real bug that would have made `alembic upgrade head` fail even when
   run in the right place, since Alembic can't find its config without it.
   Also, `scripts/seed.py` (at the repo root) was outside the backend
   image's build context (`./backend`) entirely, so it could never have
   been run in-container without restructuring. Fixed by moving the
   backend image's build context to the repo root (`docker-compose.yml` +
   `backend/Dockerfile` both updated) so the image can include both
   `alembic.ini` and the top-level `scripts/` directory. `ci.yml`'s
   Docker build step was updated to match.
3. **`make migrate` succeeded** (confirmed on your machine: `Running
   upgrade -> 0001, initial schema`), but `make seed` then hit a real
   `passlib`/`bcrypt` version-incompatibility bug: passlib 1.7.4 predates
   bcrypt's 4.1+ API changes (bcrypt removed `__about__`, which passlib's
   backend-detection code reads), surfacing as a confusing "password
   cannot be longer than 72 bytes" error on the *first* `pwd_context.hash()`
   call rather than an obvious version mismatch. Reproduced and fixed in
   this sandbox: pinned `bcrypt>=4.0.1,<4.1` in `backend/pyproject.toml`,
   confirmed the exact `pwd_context.hash(...)` call from `seed.py` now
   succeeds and verifies correctly, and added a regression test
   (`tests/test_password_hashing.py`) so a future dependency bump that
   drops the pin gets caught by CI instead of a live seed run.
   **This fix needs the backend image rebuilt** (`make up-d` again, since
   it rebuilds on `docker compose up --build`) before `make seed` will
   pick up the corrected dependency.
4. Separately, from the earlier attempt: your terminal session showed
   `make up` running attached, then a Ctrl+C ("Gracefully Stopping...")
   which stopped all 4 containers. Added a `make up-d` target (detached)
   to avoid this trip-up going forward — confirmed working on your
   machine in the run that produced bug #3 above.
